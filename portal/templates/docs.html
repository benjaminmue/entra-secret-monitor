App-Registrierung im Kundentenant

Pro Kunde wird einmalig eine App-Registrierung mit genau einer Anwendungsberechtigung angelegt. Danach liest das Portal die Ablaufdaten aller Credentials des Tenants, ohne irgendetwas verändern zu können.

Benötigte Berechtigung

APIBerechtigungTypZustimmung
{{ permission.api }} {{ permission.name }} {{ permission.type }} {{ permission.consent }}
Nur lesend. Application.Read.All erlaubt keine Änderung an App-Registrierungen, keinen Zugriff auf Postfächer, Dateien oder Benutzerdaten. Die ID der Berechtigung lautet {{ permission.id }}.
Weder Directory.Read.All noch eine Verzeichnisrolle sind nötig. Wer beim Konsens versehentlich mehr erteilt, gibt dem Portal mehr Rechte als es je verwendet.

Variante A: mit dem mitgelieferten Skript

Legt die App-Registrierung an, erzeugt ein Zertifikat, hinterlegt den öffentlichen Teil im Tenant und gibt Zertifikat und Schlüssel als PEM aus. Benötigt PowerShell 7 und einen Anmeldung als Anwendungsadministrator.

pwsh -File .\scripts\New-MonitorAppRegistration.ps1 `
  -TenantId <tenant-guid> `
  -TenantKey <kundenschlüssel> `
  -CreateCertificate

Die Ausgabe enthält Tenant-ID, Client-ID sowie die beiden PEM-Blöcke. Beides wird im Formular Kunde anlegen eingefügt.

Variante B: von Hand im Entra-Portal

  1. Entra-Portal, Identität > Anwendungen > App-Registrierungen > Neue Registrierung. Name zum Beispiel SVC-Monitoring-SecretExpiry, Kontotyp "Nur Konten in diesem Organisationsverzeichnis", keine Umleitungs-URI.
  2. In der neuen Registrierung API-Berechtigungen > Berechtigung hinzufügen > Microsoft Graph > Anwendungsberechtigungen, danach {{ permission.name }} auswählen.
  3. Administratorzustimmung erteilen anklicken. Ohne diesen Schritt liefert Graph beim ersten Lauf einen 403.
  4. Zertifikat erzeugen und den öffentlichen Teil unter Zertifikate & Geheimnisse > Zertifikate hochladen. Alternativ dort ein Client Secret erstellen, maximale Laufzeit 24 Monate.
  5. Aus der Übersicht Anwendungs-ID und Verzeichnis-ID notieren.
# Zertifikat und Schlüssel lokal erzeugen (OpenSSL)
openssl req -x509 -newkey rsa:2048 -sha256 -days 3650 -nodes \
  -keyout kunde.key -out kunde.crt -subj "/CN=entra-secret-monitor"

Der Inhalt von kunde.crt gehört in das Feld Zertifikat, der Inhalt von kunde.key in das Feld privater Schlüssel. Im Entra-Portal wird nur kunde.crt hochgeladen.

PRTG-Sensor

Sensortyp HTTP Data Advanced, Intervall sechs Stunden. Der Abruf liest den gespeicherten Stand aus der Datenbank und löst keine Anfrage an Microsoft aus.

{{ base }}/prtg/<token>
  • Kanal Datenalter schlägt an, wenn der tägliche Lauf ausbleibt. Warnung ab {{ cfg.stale_hours }} Stunden, Fehler ab {{ cfg.stale_hours * 2 }} Stunden.
  • Kanal Minimale Restlaufzeit trägt die Warn- und Fehlergrenze des Kunden.
  • PRTG ordnet Kanäle über den Namen zu. Grenzwerte werden nur beim ersten Auftreten eines Kanals übernommen, spätere Änderungen müssen im Sensor nachgezogen werden.
  • Der Token gilt für genau einen Kunden und lässt sich in der Kundenansicht erneuern, ohne ein Konto anzufassen.

Sensor für eine einzelne Anwendung

Derselbe Token bedient beliebig viele Sensoren. Gefiltert wird der gespeicherte Stand, ein zusätzlicher Sensor kostet also keine weitere Graph-Anfrage. In der Kundenansicht führt neben jedem Credential ein Link XML direkt auf die passende URL.

# alles ausser dem selbst rotierenden Connect-Zertifikat, Schwellen 30/14
{{ base }}/prtg/<token>?exclude=ConnectSyncProvisioning

# nur das Connect-Zertifikat, Schwellen 10/5, damit ein stehender
# Connect-Server trotzdem auffällt
{{ base }}/prtg/<token>?filter=ConnectSyncProvisioning&warn=10&error=5

# genau eine Anwendung
{{ base }}/prtg/<token>?app=KeyCloak&type=secret
ParameterWirkung
appgenau diese Anwendung, exakter Name

Die Kennzahlen Minimale Restlaufzeit, Kritisch und Abgelaufen werden über den gefilterten Umfang neu berechnet. Ein Sensor beschreibt damit immer nur seinen eigenen Ausschnitt.
